# Avito Architecture — Layering & Generated Code

**Activates when**: `app.toml` present, or `brief/` directory, or `internal/generated/` / `__generated__/` directory exists.

**Used by**: `architect-reviewer`, `golang-pro`, `typescript-pro`, `frontend-developer`.

## Mandatory layering

### Go (PaaS / APICO / Brief)

- Handler is a **thin transport slice**. No business branching, no orchestration, no error-mapping logic — just decode request, call use-case, encode response.
- Generated RPC client (`internal/generated/`, `*_gen.go`, `clients/*.brief` artefacts) must **never** be called directly from a handler. Always go through a `provider` / `use-case` layer.
- Repository contains persistence only — no orchestration of multiple external systems, no domain logic.
- Service / use-case owns business logic and is the only layer allowed to compose repositories + external clients.
- Transactions started/closed at the use-case layer, never inside repositories.

Findings on Go:

| Pattern | Severity |
|---|---|
| Handler calls generated RPC client directly | P1 (architecture violation) |
| Handler contains business branching, status mapping, or side-effect collection | P1 |
| Repository orchestrates multiple external clients | P1 |
| Service returns HTTP-specific errors (`http.StatusNotFound`) instead of domain errors | P2 |
| Middleware contains product rules, not transport concerns | P2 |

### Frontend (Brief / APICO TypeScript)

- Transport layer (Brief/APICO clients) is generated. Generated files are read-only.
- Business logic lives in domain modules, not in transport.
- UI layer must not import transport internals directly — go through a feature / domain adapter.

Findings on frontend:

| Pattern | Severity |
|---|---|
| Generated file (`generated/`, `__generated__/`, `*.gen.ts`, `*.generated.ts`) hand-edited | P0 (will be overwritten next codegen) |
| UI component imports transport client directly, bypassing domain layer | P2 |
| Hardcoded routes / constants that have a documented single source of truth | P2 |

## Generated-code exclusion

These paths are **never** commented on directly — they are autogenerated and any change must come from the source schema, not the file:

- Go: `internal/generated/`, `*_generated.go`, `*_gen.go`, `*_mock.go`
- Frontend: `generated/`, `__generated__/`, `*.generated.ts`, `*.gen.ts`

Exception: a *hand-edit* of one of these files **is** a finding (the hand-edit is the bug, not the file contents).

## Shared-util discipline

Shared utility (`pkg/utils/`, `internal/common/`) must not:

- mutate domain state
- emit side effects (logs/metrics OK; clickstream/databus/queue events not OK)
- depend on transport or repository layers (utils are leaves)

A shared util that mutates state or emits a business event → P1 finding.

## DI / Locator discipline (Go)

Avito Go services use a Locator + `Once[T]` pattern. Rules the reviewer enforces:

- **Locator is passed only to constructors.** A struct never stores `*Locator` as a field. Struct fields hold **concrete dependency interfaces**, not the locator.
- **Why**: storing the locator hides which dependencies a type actually uses and blocks mock generation — mockgen / hand-mocks need explicit interfaces on fields, not a god-object.
- **What to flag (P1)**: a new struct declared in the diff has a `loc *locator.Locator` (or equivalent) field; constructor body wires the locator into the struct instead of resolving deps and storing them.

```go
// BAD — locator stored, deps invisible, can't mock
type Service struct {
    loc *locator.Locator
}
func NewService(loc *locator.Locator) *Service {
    return &Service{loc: loc}
}
func (s *Service) Do(ctx context.Context) error {
    return locator.Get[UserRepo](s.loc).Find(ctx, ...)  // hidden dependency
}

// GOOD — locator only at construction; struct holds explicit interfaces
type Service struct {
    users UserRepo
    cache Cache
}
func NewService(loc *locator.Locator) *Service {
    return &Service{
        users: locator.Get[UserRepo](loc),
        cache: locator.Get[Cache](loc),
    }
}
```

## Entrypoints (cmd/, crons, workers)

- `cmd/<binary>/` may contain **multiple files** — not a single-file mandate. Splitting `main.go` into `wire.go` / `flags.go` / `signal.go` is current practice. **Never** flag "too many files in cmd/" — it's not a finding.
- **Cron / worker binaries must be built in `Dockerfile`** alongside the main binary. A new cron added under `cmd/` without a corresponding `RUN go build` (or build target consumed by the Dockerfile) → **P1** (binary won't be in the image; cron won't run in production).
- Each cron/worker entrypoint reads its schedule and resource limits from `app.toml` (`[[crons]]` / `[[workers]]` sections). Missing entry there → cross-flag with `config-completeness.md`.

## Cross-cutting smells (any layer)

- **God service** — single service file owns 5+ unrelated domains. Flag and recommend split.
- **Cyclic dependency** — package A imports B, B imports A directly or transitively. Use `go list -deps` / TS module graph to confirm.
- **Knowledge leak** — domain concept (e.g. tariff rules) implemented in two layers; flag the duplicate that's not the source of truth.
- **Double observability** — same operation logged + metric'd at handler and service and repository. Pick one layer.

## Quick checklist

1. Handler thin? No business branching, no generated-client calls, no error mapping.
2. Generated files unmodified?
3. Repository persistence-only?
4. Transactions at use-case layer only?
5. Shared utils side-effect-free (beyond logs/metrics)?
6. UI uses domain adapter, not transport client?
7. New struct: deps as explicit interface fields, **not** stored Locator?
8. New cron/worker entrypoint has a Dockerfile build step?
