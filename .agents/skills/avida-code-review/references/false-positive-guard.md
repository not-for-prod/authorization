# False-Positive Guard

The single largest practical failure of LLM code review is noise: comments that look plausible, get developers to investigate, and turn out to be wrong. This file lists patterns each reviewer agent MUST self-reject before emitting a finding.

## Universal guard (every reviewer)

Before emitting a finding, the reviewer must affirm all five:

1. **Cite the line.** The finding's `line_range` overlaps an actually-changed line in this diff. Two exceptions: (a) the diff *materially exposes* an existing issue on a nearby unchanged line (e.g. doubles its call frequency on a hot path) — keep `line_range` on the changed line; (b) a *latent finding* — a real bug on an unchanged line inside a function this diff touches but too far for `line_range` to reach — set `line_range` on the latent line **and** `evidence.enclosing_diff_line` on a changed line in the same function, category-gated per `references/output-schema.md`. Otherwise unchanged context is rejected.
2. **Quote the evidence.** The finding body either quotes the exact problematic snippet (≤5 lines) or names the file and a verifiable property ("`Foo` defined at `foo.py:42` has no tenant filter").
3. **Name the user-visible / operational impact.** "This is bad practice" is not impact. "This will return 500 on empty input" is impact. "This query degrades above 10k rows" is impact.
4. **Reachability.** For correctness, security, race, perf claims — the path is reachable. If the call site has a guard, the guard is acknowledged and the bypass is named.
5. **Project policy check.** Before flagging a "convention violation", confirm the convention is documented in `AGENTS.md` / `CLAUDE.md` or visible in adjacent files. No imaginary conventions.

A finding that cannot pass all five is dropped, not downgraded.

## Generated code — never a finding *target*

These paths are autogenerated. Lines inside them are **never** valid findings — any fix must come from changing the generator's input, not the output:

**Go**: `internal/generated/`, `*_generated.go`, `*_gen.go`, `*_mock.go`

**Frontend / TS**: `generated/`, `__generated__/`, `*.generated.ts`, `*.gen.ts`, `*.gen.tsx`

Exception: a **hand-edit of one of these files** *is* a valid finding (P0 — the edit will be lost on next codegen). The finding's `line_range` points at the hand-edit; the snippet quotes the hand-edited lines.

Drop any finding whose `line_range` is inside a generated path and whose body is not "this file was hand-edited".

## Migration / rollout false positives

When the Phase 2 intent block marks the PR as `intentional migration / cleanup`, `deprecation rollout`, or `split rollout`, additional guardrails apply.

**Do not raise** as P0/P1:

- "You removed the legacy fallback" — if the cleanup *is* the stated intent.
- "You deleted method X that is unused" — if the deletion is the stated intent.
- "You collapsed two code paths into one" — if the consolidation is the stated intent.
- "Backward compatibility broken" — if the PR is the *intentional* step of a deprecation rollout AND a sibling PR or rollout note covers the consumer side.

**Do raise** even on migration PRs:

- **Parity loss** — the new code does not preserve observable behaviour that the intent did not say to change.
- **Safety-net gap between rollout steps** — clients can call the deprecated path after this PR ships, and no fallback / dual-write / feature flag protects them.
- **Missing migration sibling** — PR removes a producer-side field but the consumer-side sibling (in this repo or another) is not referenced or in flight.
- **Intent contradiction** — the diff also does something the intent did not say to do.

Reframe rollout-shaped findings as `rollout dependency`, `migration note`, or `parity risk` rather than `bug`. See `rubric.md` for severity calibration on migrations.

## Common false-positive patterns by role

### code-reviewer

- "Variable name unclear" without a concrete misread risk → drop.
- "This could be a constant" for a literal used once → drop.
- "Could extract a function" without duplication → drop.
- "This file is too long" only when it crosses **neither** the documented project limit **nor** the 1000-line ceiling, and the PR did not push it from under 1k to over 1k → drop. Crossing either threshold is a valid finding (see rule 1 in `references/maintainability.md`).

### security-auditor

- "Hardcoded secret" when the string is in `.env.example`, a test fixture clearly marked as such, or a public key meant to be public → drop.
- "SQL injection" when the call uses a parameterised driver / query builder (`?`, `$1`, `.where(col, val)`, `text(... :param ...)`) → drop.
- "Weak hash" when MD5/SHA-1 is used for non-security purposes (checksum, cache key, fingerprint) → drop.
- "Missing auth" when the route is mounted under a middleware that enforces it; trace the registration before flagging.
- "XSS" when output is going through the framework's auto-escaping (`React`, `Vue` text, Jinja autoescape) and is not `dangerouslySetInnerHTML` / `mark_safe` / `v-html`.

### qa-expert

- "Missing test" when the test exists in a sibling file the reviewer didn't read.
- "Race condition" without naming the two operations and their interleaving.
- "Idempotency break" without naming the retried operation.
- "Error swallowed" when the error is wrapped/logged at a higher layer (trace the call site).

### architect-reviewer

- "Layering violation" without quoting the documented layering from `AGENTS.md`/`CLAUDE.md`.
- "Should use DI" when the project does not document a DI pattern.
- "Wrong pattern" when the cited "right pattern" is the reviewer's personal preference.

### code-simplifier

- "Overengineered" when the apparent complexity is justified by a multi-tenant, retry, idempotency, or generator-respect requirement — check `AGENTS.md`/`CLAUDE.md` first.
- "Unnecessary abstraction" for code with ≥2 real call sites.

### sql-pro

- "N+1 query" without showing the loop and the per-iteration query.
- "Missing index" without checking the migrations directory for an existing index.
- "Unsafe migration" when the documented migration playbook (`CONCURRENTLY`, `NOT VALID`, two-phase) is followed in adjacent files.

### python-pro / golang-pro / typescript-pro / react-specialist / frontend-developer / fullstack-developer

- "Wrong idiom" when the cited "correct idiom" is not in the project's existing code.
- "Type widening" when the project's `tsconfig` / `mypy.ini` permits it intentionally.
- "Missing memo" / "missing dep" for cases the React rule of hooks does not actually require.

## Verifier (fact-check) calibration

The verifier subagent is the second-level filter. It MUST:

- Open the cited file and read at least the cited line ± 30 lines.
- Open `AGENTS.md` / `CLAUDE.md` when a convention claim is made.
- For library / framework behaviour, confirm the version's actual behaviour by searching the internal platform documentation and the wider code search (how other services use the same API), official docs, or `package.json` / `go.mod` — not a training-data assumption.
- Reject anything that fails the universal guard above.

If the verifier cannot resolve confidently within its budget, mark `unconfirmed` and emit specific resolving questions. In a headless runtime an `unconfirmed` finding is **never posted to the PR** — it is dropped to the internal run summary (see SKILL.md Phase 5).

## Calibration after the run

If the final report has confirmed-rate < 30% (fewer than 30% of raised findings survived verification for two consecutive runs on similar diffs), the orchestrator surfaces a one-line note: "noise rate high — consider tightening role focus areas in `references/roles/*.md`". This is feedback for the maintainer, not for the current user's PR.
